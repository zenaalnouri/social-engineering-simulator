# Social Engineering Simulator — Backend

Flask + SQLAlchemy backend for an interactive cybersecurity-awareness
platform. Users get randomized social-engineering scenarios (phishing
emails, fake login pages, fake IT support chats, SMS scams, giveaway
scams, fake manager messages) instead of a plain quiz, then get scored
and rated on an awareness scale. The Flask app serves the existing
bilingual frontend and REST API from one origin.

## Stack

Python · Flask · SQLite · SQLAlchemy · Flask-Migrate · Flask-CORS ·
python-dotenv · Flask-RESTX (REST + Swagger docs)

## Setup

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# optionally copy .env.example to .env and set local values
copy .env.example .env        # Windows
# cp .env.example .env        # macOS/Linux

flask db init
flask db migrate -m "initial schema"
flask db upgrade

python run.py                    # serves on http://localhost:5000
```

## Response envelope

Every endpoint replies with one of:

```json
{ "success": true,  "message": "...", "data": {} }
{ "success": false, "message": "...", "error": {} }
```

## Simulation flow

1. `POST /users` — get-or-create a user by name.
2. `POST /simulation/start` — server randomly picks 5 *active*
   scenarios (no duplicates, different every call) and opens an
   attempt. Correct answers are never sent to the client.
3. `POST /simulation/answer` — submit one answer at a time. Validated
   against: attempt exists, attempt not already finished, scenario
   actually belongs to this attempt, not already answered. Updates
   the scenario's live analytics counters on every submission.
4. `POST /simulation/finish` — once all 5 scenarios are answered,
   computes score, percentage, and awareness level, and closes the
   attempt.

### A note on the data model

The spec's `AttemptAnswer` only stores `scenario_id`, not which
5 scenarios were assigned to an attempt *before* they're answered.
To satisfy the explicit validation requirements ("invalid IDs",
"duplicate submissions") this project adds one small internal table,
`AttemptScenario`, created at `/simulation/start` time, that records
which scenarios/questions belong to which attempt. `/simulation/answer`
checks against it before writing an `AttemptAnswer`. It's plumbing,
not a scored/user-facing concept.

## Awareness levels

| Percentage | Level             |
|-----------:|-------------------|
| 90–100     | Expert            |
| 70–89      | Advanced          |
| 50–69      | Intermediate      |
| < 50       | Needs Improvement |

## Endpoints

| Method | Path                                   | Purpose                             |
|--------|-----------------------------------------|--------------------------------------|
| POST   | `/users`                                | Get-or-create a user by name         |
| POST   | `/simulation/start`                     | Start a simulation (5 random scenarios) |
| POST   | `/simulation/answer`                    | Submit one answer                    |
| POST   | `/simulation/finish`                    | Finish & score a simulation attempt  |
| GET    | `/leaderboard?limit=`                   | Public leaderboard                   |
| GET    | `/admin/scenarios`                      | List all scenarios                   |
| POST   | `/admin/scenarios`                      | Create a scenario                    |
| PUT    | `/admin/scenarios/<id>`                 | Update a scenario                    |
| DELETE | `/admin/scenarios/<id>`                 | Delete a scenario                    |
| POST   | `/admin/scenarios/<id>/activate`        | Activate a scenario                  |
| POST   | `/admin/scenarios/<id>/deactivate`      | Deactivate a scenario                |
| POST   | `/admin/questions`                      | Add a question to a scenario         |
| PUT    | `/admin/questions/<id>`                 | Update a question                    |
| DELETE | `/admin/questions/<id>`                 | Delete a question                    |
| GET    | `/admin/results/users/<user_id>`        | A user's completed simulations       |
| GET    | `/admin/results/simulations`            | All completed simulations            |
| GET    | `/analytics`                            | Platform-wide analytics              |
| GET    | `/analytics/scenarios`                  | Per-scenario analytics + callouts    |
| GET    | `/reports`                              | Dashboard statistics                 |

Valid `type` values for a scenario: `phishing_email`, `fake_login_page`,
`fake_it_support_chat`, `sms_scam`, `giveaway_scam`, `fake_manager_message`.
Valid `difficulty` values: `easy`, `medium`, `hard`.
Valid `correct_answer` / `selected_answer` values: `A`, `B`, `C`, `D`.
